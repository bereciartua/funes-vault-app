# ADR-0031: The iPhone answers every Inbox card

**Status:** Accepted · 2026-11-01 (after a GPT-6-Astra review of the draft against this repository) · **Amends** [ADR-0020](0020-atomic-extraction-for-every-source.md) and [ADR-0021](0021-daily-tidy-up.md) (their "Review on your Mac until the iPhone gets its own cards"), [companion protocol §4](../companion-protocol.md#4-methods), [UX: iPhone ▸ Inbox tab](../../product/05-ux-iphone.md#inbox-tab), FR-iOS-09.

## Context
- **Phase 6 left the iPhone behind on purpose.** When the Inbox gained merge, split and conflict cards and the daily tidy-up, the phone was given "Review on your Mac" for them, until it got its own cards. `inbox.list` sends every tidy-up proposal (origin `consolidation`) with action `unknown`, whatever it does, and `inbox.apply` refuses merge, split, conflict and every tidy-up proposal with `unsupported_action`. The phone can only reject them.
- **The reason was what the phone couldn't show.** Its cards carry one suggestion's own fields. A tidy-up update may also archive a copy, an archive names the memory it keeps, a merge has sources, a conflict two memories, a split its pieces. Applying any of them blind would be wrong.
- **The author's feedback (1 Nov 2026), after days of the overnight tidy-up:** most mornings' cards can only be rejected on the iPhone; "everything else, we need to go to the Mac app". The tidy-up has made about 85 such cards so far (archives, splits, merges, updates, conflicts, already-saved).
- **FunesCore already applies every action**, in one per-action apply that both the Mac's Inbox and `inbox.apply` call, with the choices a card offers (`ApplyMode`: Replace, Keep both, Keep this, Both are true) and Review Again for a stale card. Only the companion protocol and the phone's screens are missing.

## Decision
1. **Every card is answered on the iPhone,** from any origin, with the Mac card's choices: Save (create), Replace and Keep Both (update; Keep Both never for the tidy-up's, as on the Mac), Archive, Already Saved (duplicate), Split into N, Merge, and for a conflict Keep This (either memory), Both Are True and Edit…. Edit & Save stays for create, and becomes Edit & Replace for an update and Edit & Merge for a merge. `unknown` (an action from a newer Mac) stays "Review on your Mac".
2. **A card shows what it changes before it can be applied.** A new method, **`inbox.get`**, returns one suggestion in full when its screen opens: the memories it refers to with their roles and current text (an update's target and any copy it also archives, an archive's target and the memory it keeps, a merge's sources, a conflict's two memories, a split's original, a duplicate's match), a split's pieces, the tidy-up's reason (its archive reason and, for a merge, what each source keeps), whether it's stale, and the similar memories the Mac would point out. The list stays as it is, so a page of 50 doesn't carry every related memory's text.
3. **`inbox.apply` takes the card's choice** as `mode` (`replace`, `keep_both`, `keep` with `keepMemoryId`, `both_true`), the same `ApplyMode` the Mac passes. A conflict without a mode is refused with `unsupported_action`, as is `keep_both` on a tidy-up proposal. **It's bound to what the phone showed:** `inbox.get` returns a `revision` (a hash of the suggestion's fields, its memories' ids, roles, stored and current versions, and a split's pieces), and an apply from the card's screen sends it back. A different one is `request_changed`, and the screen fetches the card again. So a card shown before a change on the Mac (an edit there, then Review Again there) can't be applied against what the phone never showed.
4. **Review Again works from the phone** (`inbox.reviewAgain`): a stale card says "Changed since this was suggested", its apply buttons are off (Keep Both and Reject stay, as on the Mac) until Review Again records the current versions and the screen shows the memories as they are now.
5. **Swipe right only where the row shows everything that changes:** Save on a new memory, and Already Saved on a duplicate (which changes nothing). Every other card opens to be answered, since what it changes (the memory it replaces, archives or keeps, a merge's sources, a split's pieces) is only on its screen. That drops the swipe that saved an agent's correction without showing the memory it replaces.
6. **Out of scope:** the Applied automatically list and its Undo, Later, Apply N, and a split input's group actions (Apply All and its Keep as One, which undoes a successful split) stay on the Mac. Each of a split input's pieces is still answered on the phone, as since v0.3; none of these is needed to answer a card.

## Consequences
- **One fix in FunesCore:** a memory deleted for good leaves an update's, an archive's, a duplicate's or a split's single target null (`ON DELETE SET NULL`), so `isStale` said "not stale" and Review Again succeeded while Apply refused with `target_changed`. A suggestion with a target version but no target is now stale, and Review Again refuses it. The Mac's card benefits too.
- **No change in what a phone may do:** it's the owner ([access policy §6](../../domain/access-policy.md#6-owner-devices-paired-iphone)) and could already read every memory `inbox.get` returns with `memories.get`. `inbox.get` logs `inbox_viewed` and Review Again `suggestion_reviewed_again`, each with the suggestion's id, never text.
- **Both apps are updated together** (no external users), so the Mac doesn't check the phone's version. An older phone given a tidy-up card with its real action could apply it without seeing the memory it keeps; that's acceptable here and not worth a version check.
- **The phone's suggestion screen grows one layout per action,** in the app target; the calls are in `FunesPhone`'s `InboxModel`, with tests against a fake vault, and the demo vault gets tidy-up cards.
- **The words match the Mac's Inbox** ("Archives “…”", "Keeps “…”", "Merges 3 memories into one", "These disagree. Which is true?").

## Alternatives considered
- **Send the related memories in `inbox.list`:** one call fewer, but every page would carry the full text of every memory every card refers to, most of it never opened.
- **Only the tidy-up's archives and duplicates:** the cards the author sees most, but merges, splits and conflicts would still need the Mac, which is the complaint.
- **Open the memory with `memories.get` for each reference:** works for text, but the roles, the pieces, the tidy-up's reason and staleness aren't in it, and it's several calls per card.
